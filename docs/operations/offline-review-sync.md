# 离线评分补交的服务端规则

手机端（PWA）离线时把评分存在本地队列，联网后按顺序补交到
`POST /api/mistakes/{id}/review`（客户端见 [../integration/pwa.md](../integration/pwa.md)，
`static/offline-sync.js`）。本文只写服务端怎么处理这些补交请求。

## 请求

在原有 `quality`、`version` 之外，评分接口多接受两个**可选**字段：

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `client_op_id` | 字符串 | 匹配 `^[A-Za-z0-9_-]{8,64}$`；客户端为每次评分生成一个，重试时必须沿用 |
| `reviewed_at` | ISO 时间 | 必须带时区（`Z` 或 `+08:00`），例如 `2026-09-18T06:00:00.123Z`；数字时间戳、没有时区的时间一律 422 |

- 两个字段都不传：行为与以前完全一致（评分时间取服务器当前时间，“今天”取服务器上的用户本地日期）。
- **`version`**：不带 `client_op_id` 时仍然必填；带 `client_op_id` 时可以省略（离线时可能没有预取到版本号），
  省略则不做版本比较，其余检查照常。带了就照常比较，不一致返回 409。
- 响应与原来完全一致：`repetitions`、`interval_days`、`ease_factor`、`due_date`、`version`，没有新增字段。

## 幂等（`client_op_id`）

- 表 `review_ops`（迁移 13），主键 `(user_id, client_op_id)`，保存 `mistake_id`、第一次的响应 JSON、`created_at`。
- 同一用户用同一个 `client_op_id` 再次提交：**不再评分**，直接返回第一次保存的响应（HTTP 200，内容相同），
  不重新校验版本、`reviewed_at`、到期状态——客户端重试、响应丢失后重发都是安全的。
- 不同用户的相同 id 互不影响；一个用户看不到、也无法重放别人的记录。
- 同一个 id 用在另一道题上：422（客户端 bug，不会静默返回别的题的结果）。
- “先查后写”在同一个写事务（`BEGIN IMMEDIATE`）里完成，并发的重复提交在写锁上排队，只有第一个生效，
  其余拿到同一份保存的响应。
- **只有成功的评分才会被记录。** 返回 4xx 的请求（暂停、未到期、版本冲突、时间不合法）不留记录，
  条件改变后可以用同一个 id 重试。
- 清理：每个带 `client_op_id` 的评分请求会顺手删除 `created_at` 早于 30 天的记录（恰好 30 天的保留）。
  清理后同一个 id 再到达会被当作新操作；而 `reviewed_at` 最多只允许回溯 7 天，所以不会误重评。

## `reviewed_at` 的规则

按下面的顺序判断，**重复提交（幂等命中）在这些检查之前直接返回**：

1. 晚于服务器当前时间 + 60 秒 → **422**「评分时间不能晚于当前时间」（容忍客户端时钟略快；恰好 +60 秒允许）。
2. 早于当前时间 7 天前 → **422**「评分时间不能早于 7 天前」（恰好 7 天允许）。
3. 早于这道题上一次评分的时间（`last_reviewed_at`）→ **409**「这道题之后已经有更新的评分」
   （同一秒不算早于）。客户端把 409 当作“已处理”跳过，不重试。
4. 之后是原有检查：版本（若带）→ 已暂停（409）→ 尚未到期（409）。

通过后，`reviewed_at`（换算成 UTC、截断到秒）用作这次评分的时间：

- **调度**：“今天”取 `reviewed_at` 按用户本地时区换算出的日期，下次到期日和逾期天数都从这一天算，
  不是服务器收到请求的那天。
- **复习日志与 `last_reviewed_at`**：写入 `reviewed_at`；热力图、连续打卡、统计、榜单读的都是这份日志，
  所以补交的评分记在当时做题的那一天（用户本地日）。
- 跨日示例：上海用户 `2026-09-18T16:00:00Z` 的评分属于上海的 9 月 19 日；同一时刻洛杉矶用户属于 9 月 18 日。

## 每日上限

每日复习上限（`daily_review_cap`）只决定今日复习队列一次放出多少题，评分接口**从不**因为超过上限而拒绝。
补交评分按 `reviewed_at` 所在的**用户本地日期**计入当天的“今日已做”：

- 昨天离线做的题，今天联网补交后算昨天的，不会占用今天的名额；
- 跨过本地午夜的评分算次日（UTC 日期不同于本地日期时以本地日期为准）；
- 昨天做超过上限的题，补交时全部接受。

这样取舍是为了不丢用户真实做过的复习，也不让补交压缩当天的新队列。

## 与撤销、暂停、推迟的交互

- **撤销**：撤销的 30 分钟窗口仍按复习日志里的 `reviewed_at` 计算，即“补交评分的时间”距现在不超过 30 分钟才能撤销；
  离线补交的旧评分通常已经超过窗口（409「超过 30 分钟，不能撤销」）。
  **被撤销之后，同一个 `client_op_id` 再次到达，仍返回第一次保存的响应，不会重新评分**，
  记录也不会因撤销而删除（直到 30 天清理）。撤销后想重新评分，要使用新的 `client_op_id`。
- **暂停**：对已暂停的题评分，行为保持不变（409「这条易错点已暂停，请先恢复」），不留幂等记录；
  评分成功之后才被暂停的，重复提交仍返回第一次的响应。
- **推迟**：推迟会把到期日往后挪。离线评分的“当天”如果这道题（因为在别的设备上被推迟）还没到期，补交返回 409「尚未到期」，
  客户端当作已处理跳过。
- 题目已被删除：没有幂等记录的补交返回 404（客户端计入“已跳过”）；已有记录的重复提交仍返回保存的响应。
- 注销账号会删除该用户的全部幂等记录。

## 静态入口

- `GET /sw.js`：内容为 `static/sw.js`，`Content-Type: text/javascript; charset=utf-8`，
  `Service-Worker-Allowed: /`，`Cache-Control: no-cache`。Service Worker 必须从站点根路径提供才能控制整站。
- `GET /manifest.webmanifest`：内容为 `static/manifest.webmanifest`，`Content-Type: application/manifest+json`，
  `Cache-Control: no-cache`。
- 图标等其他文件走现有的 `/static`。内容安全策略（CSP）不变，没有放宽。

## 升级与回滚

- 迁移 13 新增表 `review_ops`，启动时自动迁移，无需手工操作。
- 先上线服务端、再发布前端：服务端对旧客户端（不带新字段）完全兼容。
- 回滚程序版本前请先备份（见 [backup-and-restore.md](backup-and-restore.md)）；旧版程序拒绝打开更新的数据库。

## 排查

```sql
-- 某个用户最近的补交记录
SELECT client_op_id, mistake_id, created_at FROM review_ops WHERE user_id = ? ORDER BY created_at DESC LIMIT 20;
```

变异检查（去掉幂等判断 / reviewed_at 上界 / 早于上次评分的检查，测试必须失败）：
