# 手动收款（个人收款码 + 付款登记 + 兑换码）

站点没有接入支付渠道时，用“个人收款码”收款。个人收款码无法自动得知有人付了钱，所以做成**半自动**：用户付款后登记，站长核对到账后一键确认，系统自动开通套餐。

## 金额如何确定

- **官方订单**：可购买套餐的按钮支持选择支付宝或微信。`POST /api/orders` 只接受
  套餐和渠道；服务端按套餐价格保存订单金额快照，再传给官方支付适配器。
  用户无需输入付款金额，也不能通过请求自行指定金额。支付回调必须与订单金额一致。
  站长须先配置对应的官方支付渠道；代码提供入口并不代表真实渠道已配置或已验收。
- **个人通用码**：页面展示套餐价格，但付款 App 的金额仍由用户输入，网页无法锁定。
  新的手动登记由服务端在同一写事务中保存当时的金额（整数分）、时长与套餐名称快照。
  待处理期间调价或修改时长、名称不会改变该登记的核账金额与开通天数。
  这份快照不会证明到账；站长必须在收款 App 的真实账单中核对金额与完整流水号后再确认。

上传通用收款码后，不要把页面提示当成“固定金额二维码”。要免除用户输入金额，
应使用已配置的官方订单支付，或另外核实支付平台生成的套餐专用固定金额码；
本轮没有新增此类二维码的配置或校验。

## 流程

1. **用户付款**：在套餐页扫描站长配置的收款码（后台“手动收款设置”里上传支付宝/微信二维码并填写联系方式）。
2. **用户登记“我已付款”**：选择套餐，填写付款备注（≤ 60 字，建议写支付账号昵称或尾号、付款时间），联系方式可选（≤ 60 字）。接口 `POST /api/manual-claims`。
   - 体验账号不能登记；同一用户最多同时有 3 条待处理登记；每个用户每天最多提交 5 次；只能选当前在售的套餐。
3. **站长核对并确认**：在收款 App 里核对金额与备注，在后台填写实际到账金额、渠道与完整流水号，再点“确认收款”（`POST /api/admin/manual-claims/{id}/confirm`）。金额不预填，避免把应付价格直接当成实收。
   接口要求 `verified_amount_cents`（严格正整数分）和 `receipt_reference`（`alipay:` 或 `wechat:` 加完整流水号，只允许 ASCII 字母、数字、下划线、短横线）。确认与开通在同一个数据库写事务里完成：
   - 实收金额必须等于登记时的快照金额，否则返回 409，登记仍待处理，权益不变；新登记不能人工覆盖已冻结的天数；
   - 同一渠道的同一流水号只能用于一次开通；两个管理员并发确认相同流水只会成功一次，另一条仍待处理；
   - 套餐时长的叠加口径与兑换码、管理员直接开通完全一致（未过期从原到期时间顺延，已过期从现在起算，切换套餐不折算）；
   - 同一条登记只会开通一次，重复点击或并发点击后面的请求返回 409；
   - 用户已注销、被封禁或是体验账号时拒绝确认（409），登记保持待处理。
4. **没收到款就驳回**：`POST /api/admin/manual-claims/{id}/reject`，必须写原因（≤ 80 字），用户在套餐页能看到原因。
5. **用户看到结果**：用户下次打开套餐页，登记状态变为“已开通”。若服务器配置了 SMTP（见 [mail.md](mail.md)）且用户填过邮箱，确认后还会在后台发一封简短邮件；邮件失败只写日志，不影响确认。

兑换码仍然可用：站长也可以收款后直接发兑换码（后台“兑换码”页或下面的命令行批量生成），用户在套餐页兑换。

## 命令行

在服务器上，与 `admin_tool.py` 其他命令一样直接操作数据库：

```bash
python -B admin_tool.py pending-claims                      # 列出待处理登记（编号、用户、套餐、备注）
python -B admin_tool.py confirm-claim 12 --received-cents 990 --receipt alipay:实际完整流水号
python -B admin_tool.py reject-claim 12 --reason "没有收到款"  # 驳回
python -B admin_tool.py make-codes --plan 1 --count 10 --note "10 月活动"  # 批量生成兑换码
```

- `make-codes` 的明文兑换码**只在这一次输出里出现**，数据库只存哈希；可选 `--days`（覆盖套餐默认天数）、`--expires-in-days`。请直接保存到密码管理器或发给买家，不要贴进聊天群记录或工单。
- 命令行确认/驳回不带管理员账号，登记里的“操作者”为空，日志里记为“命令行”。

### 升级前的旧登记

迁移 22 不猜测过去的价格、名称或时长。旧行的三项快照保持 NULL，界面明确显示历史信息未知。
必须核对原始到账记录，并明确填写实际到账金额与应开通天数。API 额外要求
`legacy_reviewed: true` 与 `legacy_period_days`（1–3650）；命令行示例：

```bash
python -B admin_tool.py confirm-claim 12 --received-cents 990 --receipt wechat:实际完整流水号 --legacy-reviewed --legacy-days 30
```

实收金额保存到核账字段，确认的时长保存到兑换审计；原来的历史快照仍为 NULL。
不要把当前套餐价格当成当年的成交金额。旧的已确认记录没有流水凭证，无法补做自动去重。

## 审计与隐私

- 每条登记保存提交时间、处理时间、处理人（`manual_payment_claims.decided_at / decided_by`）、冻结的金额/时长/名称，以及确认时填写的实收金额和渠道流水；确认时还会写一条“手动收款确认 #登记号：用户名”的兑换记录，后台“兑换码”列表里可以看到。
- 服务器日志只记录登记号、用户编号、套餐编号和操作者，**不打印联系方式和付款备注**。
- 用户只能看到自己的登记；注销账号时会删除其全部登记（兑换记录按财务要求保留）。兑换审计的 `code_hash` 保存带独立用途前缀的流水 SHA256，不保存明文流水；因此注销后同一流水仍不能再次开通。尚未登记流水的旧财务记录无法追溯。

## 对账建议

- 每天（或每次收到付款）先在后台处理待确认队列，别积压。收款 App 流水里的付款备注/时间应与登记的“付款备注”对得上，对不上先联系用户再驳回，不要直接确认。
- 每周或每月把收款 App 的流水导出，与“已确认”的登记逐条核对：金额、时间、用户名应能一一对应；已确认但流水里找不到的，优先排查是否误确认。
- 一个用户短时间重复登记相同备注，通常是重复点击或想“碰运气”，确认前检查是否已有同一笔付款的已确认记录。
- 误确认时：目前没有“撤销确认”接口，请用 `grant`/管理员直接开通或数据库修正到期时间，并在对账记录里留下说明。

## 官方渠道配置的离线检查

准备启用支付宝或微信官方订单前，可使用 [payment-config-check.md](payment-config-check.md) 中的离线检查工具。
检查通过仅说明所给配置的格式与本机依赖符合规则，不能证明商户权限、密钥所属关系、回调公网可达或实际交易成功。
本次验收不连接真实支付平台、不发邮件，也不在服务器安装或启用任何服务。

正式订单已经冻结金额，但其现有开通/退款时长仍读取套餐当前时长；这项历史设计本轮未改动。
人工核账登记使用本次新增的时长快照。需要调整正式订单的时长快照时应另做迁移和回归。

## 数据库与升级

- 迁移 52 追加用户手填的 `actual_paid_cents` 和可选 `payer_receipt`。套餐页实际付款金额
  默认留空，必须由用户手动填写，最多两位小数；凭证支持流水号或文字说明，不新增上传入口。
  用户提交“我已付款”只会生成待核对登记，实付与套餐快照标价不一致时明确提示人工核对。
  用户的申报金额不等于已验证到账；站长仍须在收款 App 查到账记录，并手填实收金额与完整流水后确认。
  历史登记的用户申报金额保持 NULL，不按套餐价格推算。

- 迁移 11 新增表 `manual_payment_claims`（`status` 为 `pending/confirmed/rejected`）；升级无需手工操作，启动时自动迁移。回滚程序版本前请先备份（见 [backup-and-restore.md](backup-and-restore.md)）。
- 迁移 22 追加五个可空核账字段与非空流水唯一索引；历史快照保持未知，已有已确认记录不伪造凭证。新程序的 API 与 CLI 确认操作都必须提交核账信息，不再支持空请求体或仅登记编号直接开通。
