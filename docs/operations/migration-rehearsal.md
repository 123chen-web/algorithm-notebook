# 数据库升级演练（上线前必做）

上线前，用**一份真实备份**在本机演练一次数据库升级：
验证迁移链完整、数据不丢失，并估计上线停机时间。
演练只读备份、只升级临时目录里的副本，**绝不碰线上数据库**。

## 1. 到哪里拿备份

备份由 `backup.py` 产生（tar.gz，里面是 `notebook.db` + `avatars/` +
`MANIFEST.json`）。找负责运维的人要一份最新的备份文件，
拷到你自己的电脑上。**不要直接在服务器上演练**，要在你本机演练。

## 2. 怎么运行

```bash
# 在仓库根目录执行
python tools/migration_rehearsal.py /path/to/backup-2026-10-09.tar.gz

# 也可以指定临时目录和报告位置
python tools/migration_rehearsal.py /path/to/backup.tar.gz \
--workdir /tmp/rehearsal \
--report /tmp/rehearsal-report.txt
```

要求：Python 3.9+，仓库依赖已安装（`pip install -r requirements.txt`）。
不需要联网，不调用 AI / 邮件 / 支付。

## 3. 看什么算通过

控制台最后会打印结论。**通过**长这样：

```
[✓] 升级后 user_version=22，期望 22
[✓] users：120 → 120 行
...
[✓] integrity_check=ok，foreign_key_check 无违规
[✓] 原备份文件字节完全一致，未被修改
============================================================
结论：通过。备份可以在上线时按此流程升级。
停机时间估计：升级本身约 3.42 秒（另加备份/恢复操作时间）。
============================================================
```

通过标准（缺一不可）：
- 升级后 `user_version` 等于最新迁移号；
- 用户数/题目数/易错点数/复习记录数**没有减少**；
- `integrity_check` 通过、`foreign_key_check` 无违规；
- 核心查询抽样全部执行成功；
- 重复启动无变化（幂等）、空库冷启动成功；
- 原备份 sha256 演练前后一致。

## 4. 看到什么算失败，以及怎么办

失败的行会标 `✗`，结论里会列出所有失败项：

| 现象 | 含义 | 怎么办 |
|---|---|---|
| `升级失败：user_version 停在 N，疑似出错的迁移是 M（…）` | 某个迁移在备份数据上报错 | **不要上线**。把完整报告发给开发，定位迁移 M 在旧数据上的问题，修好后再演练 |
| `users：120 → 118 行，数据减少！` | 迁移丢了数据 | **不要上线**。同上，找开发 |
| `integrity_check 未通过` / `外键违规` | 升级后数据库损坏 | **不要上线**。同上 |
| `备份里没有找到 notebook.db` | 拿到的不是 backup.py 产生的备份 | 重新找运维要正确格式的备份 |
| 核心查询抽样某条 `执行失败` | 升级后关键表/列缺失 | **不要上线**。找开发 |

任何一项失败 = 演练不通过 = **不能按原计划上线**。
修好问题后，用同一份备份重新跑一遍，直到通过。

## 5. 报告去哪了

- 控制台直接打印中文报告。
- 加 `--report` 会同时写成 txt 文件。
- 临时工作目录（解出的副本、冷启动库）默认留在系统临时目录，
排查完可手动删除。

## 6. 和上线流程的关系

演练通过 ≠ 上线完成。演练只验证"数据库升级"这一步。
上线当天仍要：先停服务 → 再做一次新备份 → 升级 → 跑一遍冒烟测试 →
确认无误再开服务。停机时间 ≈ 演练报告里的升级耗时 + 备份/恢复时间。
