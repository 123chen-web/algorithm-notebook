# 上线安全清单

> 上线前逐项打勾。每一项都写了"怎么做"和"怎么验证"。
> 标 ⚠️ 的是**不做会有实质风险**的项，不要跳过。

## 1. 服务器登录安全

- [ ] ⚠️ **SSH 改用密钥登录，禁用密码登录**
  - 怎么做：在云厂商控制台或 `ssh-copy-id` 把你的公钥放到服务器 `~/.ssh/authorized_keys`，
    确认能免密登录后，编辑 `/etc/ssh/sshd_config`，设置
    `PasswordAuthentication no` 和 `PermitRootLogin prohibit-password`，
    然后 `systemctl restart sshd`。
  - 怎么验证：另开一个终端，用密码登录应被拒绝；密钥登录正常。
    **注意：改之前务必先确认密钥登录可用，否则会把自己锁在外面**（只能去云厂商网页终端救）。

- [ ] **改掉默认的 root 密码**（第 1 步设密码时已做，买机器时选了密钥的跳过）
  - 怎么做：`passwd` 按提示重设，存到密码管理器。

- [ ] ⚠️ **确认防火墙只开了 22/80/443**
  - 怎么做：`install.sh` 已配置。验证：`ufw status verbose`，
    应该只看到 22、80、443 三条 ALLOW，没有别的端口。

- [ ] （可选）**装 fail2ban 防暴力破解**
  - 怎么做：`apt-get install -y fail2ban`，默认配置即可，
    它会自动封禁短时间内多次输错 SSH 密码的 IP。
  - 说明：如果你已经按第一条禁用了密码登录，这条是锦上添花，不装也行。

- [ ] **开启自动安全更新**
  - 怎么做：`apt-get install -y unattended-upgrades`，
    然后 `dpkg-reconfigure -plow unattended-upgrades` 选 Yes。
  - 作用：系统安全补丁自动装，不用你半夜爬起来升级。

## 2. 密钥与数据保护

- [ ] ⚠️ **`.env` 权限是 600，且没有提交到 Git**
  - 怎么做：`chmod 600 /srv/algorithm-notebook/.env`。
  - 怎么验证：
    ```bash
    ls -l /srv/algorithm-notebook/.env        # 应显示 -rw-------
    cd /srv/algorithm-notebook && git status --short | grep -c "^\s*M\{0,1\}\s.env$" || echo "未被跟踪/未修改：正常"
    git check-ignore .env && echo ".env 已被 git 忽略：正常"
    ```
  - 仓库的 `.gitignore` 本来就排除了 `.env`，这是双保险。

- [ ] ⚠️ **`data/` 目录没有提交到 Git**
  - 怎么验证：`git check-ignore data && echo "data 已被 git 忽略：正常"`。
  - 原理：数据库和头像都在 `data/` 下，`.gitignore` 已排除；
    备份文件在 `data/backups/`，同样不会进仓库。

- [ ] ⚠️ **`.env` 的真实内容另存了一份在密码管理器**
  - 备份文件（`backup.py` 生成的 `.tar.gz`）里**没有** `.env` 的密钥。
    服务器丢了要重建时，没有这份密钥抄录就配不回 AI、邮件、支付。

- [ ] **备份文件不在公开位置，且定期下载到本地**
  - 怎么做：备份默认在 `/srv/algorithm-notebook/data/backups/`（服务器本地目录，
    外部访问不到）；每月用 scp 或云厂商文件管理下载一份到自己电脑。
    备份里有密码哈希和用户数据，自己电脑上的那份也要放好。

## 3. 应用层安全验证

- [ ] ⚠️ **邀请码已换成强口令**
  - 怎么验证：`grep '^INVITE_CODE=' /srv/algorithm-notebook/.env`，
    值不是 `change-me`，长度 16 位以上，无规律。
  - 风险：邀请码泄露 = 任何人都能注册。**不要把邀请码发到公开群**，
    只私发给内测用户；怀疑泄露就换一个新的并重启服务。

- [ ] ⚠️ **HTTPS 下 Cookie 带 Secure 标记**
  - 怎么做：生产 compose 已强制 `COOKIE_SECURE=1`（即使 `.env` 里忘了改也生效）。
  - 怎么验证：用 HTTPS 域名登录后，按 F12 → Application → Cookies，
    看到登录 Cookie 有 `Secure` 勾选。HTTP 明文下没有 Secure 是正常的，
    但生产环境必须全程 HTTPS。

- [ ] **验证写接口的 CSRF 校验在生效**
  - 背景：所有账号写接口要求同源前端携带 `X-CSRF-Protection: 1` 请求头。
  - 怎么验证（在服务器上执行，应**失败**才是正常的）：
    ```bash
    # 先登录拿到 Cookie（把 用户名/密码 换成你的管理员账号）
    curl -c /tmp/cj -fsS https://你的域名/api/auth/login \
      -H 'Content-Type: application/json' \
      -d '{"username":"你的用户名","password":"你的密码"}' > /dev/null
    # 不带 CSRF 头调一个写接口，应被拒绝（4xx），而不是成功
    curl -b /tmp/cj -s -o /dev/null -w "%{http_code}\n" \
      -X POST https://你的域名/api/me/sessions/revoke-others \
      -H 'Content-Type: application/json' -d '{}'
    rm -f /tmp/cj
    ```
    返回 `401/403` 说明校验在生效；如果返回 `200`，说明有异常，停服排查。

- [ ] **`PUBLIC_BASE_URL` 是真实 HTTPS 域名**
  - 怎么验证：`grep '^PUBLIC_BASE_URL=' /srv/algorithm-notebook/.env`，
    值是 `https://你的域名`。否则找回密码邮件里的链接用户点不开。

- [ ] **确认没有把管理后台暴露给公网直连**
  - 原理：生产 compose 里 app 容器不发布端口，公网只能经 Caddy 的 443 进来，
    管理接口和普通接口走同一套登录鉴权，没有"后门端口"。
  - 怎么验证：在服务器外执行 `curl --max-time 5 http://<服务器IP>:8000/healthz`，
    应**连接失败**（端口没对外开）；而 `https://你的域名/healthz` 应返回 ok。

## 5. 已知局限（写进来的目的是让你心里有数，不是让你修代码）

1. **反向代理后的客户端 IP（已处理）。**
   应用只在 Caddy 后面，限流需要真实客户端 IP。生产 compose 已设置 `TRUST_PROXY=1`，
   程序取 Caddy 追加在 `X-Forwarded-For` 最右侧的地址来计数（客户端自己伪造的项不会被采信）。
   前提：app 容器不对公网发布端口（生产 compose 已保证）；如果你改成让 app 直接对公网开放，
   必须去掉 `TRUST_PROXY`，否则别人可以伪造来源地址绕过限流。

2. **AI 并发上限、限流计数都是单进程内存实现**，当前单实例部署没问题；
   以后如果加机器/多 worker，必须先解决共享状态问题（README 部署说明里有写）。

3. **Caddy 证书自动续期依赖 80 端口一直能从公网访问**，
   不要在续期前把 80 端口关了。`status.sh` 会显示证书有效期，每月看一眼。
