## A. 错因收敛成固定词表 + 判题类型 + 最小反例

### 问题
“典型失误”“薄弱点”“今日宜忌”等统计都靠**错因标签**，但标签现在是自由输入，同一个意思被写成“边界”“边界没处理”“越界”……统计就空转。另外，算法题最关键的两项信息——**判题类型**（WA/TLE/RE…）和**最小反例**（一个能让原代码出错的小输入）——没有结构化字段，只能混在思路文字里。

### 要做的
1. **固定词表（≤12 个，每个有稳定 code、中文名、一句提示）**。建议如下，可微调但总数别超过 12：
   `boundary` 边界/特例 · `misread` 审题/漏条件 · `wrong_idea` 思路错误 · `complexity` 复杂度/超时 · `overflow` 溢出/精度 · `concept` 概念混淆 · `formula` 公式/模板记错 · `impl` 实现细节（下标、循环、变量） · `careless` 粗心/笔误 · `api` 语法/接口 · `untested` 样例/测试没覆盖 · `other` 其他。
   词表放一个后端常量里（`tags.py` 旁边或新模块），前端从接口读，不要两边各写一份。
2. **标签只能从词表里选**：`PUT /api/mistakes/{id}/tags` 和新增记录时的标签，新写入必须在词表内（422 并给出可选项）；**完整记录（非速记、非待补）每条易错点至少选 1 个**。原来的自由文字想法写进“错因描述”（那里本来就是自由文本）。
3. **迁移 80：把已有的自由标签映射进词表**。提供同义词表（把 `tags.SUGGESTED_TAGS` 和 `REASON_SUGGEST_TAGS` 里已有的写法都映射上，例如“思路错/没思路/思路错误”→`wrong_idea`，“漏条件/没读清题”→`misread`，“公式记错”→`formula`，“语法坑/语法或接口”→`api`，“测试没覆盖”→`untested`，“溢出”→`overflow`……），映射不上的归 `other`；同一条易错点映射后重复的标签要去重；迁移幂等；单元测试覆盖映射表。
4. **判题类型**：`problems.verdict TEXT NOT NULL DEFAULT ''`，取值 `WA` 答案错误 · `TLE` 超时 · `MLE` 超内存 · `RE` 运行错误 · `CE` 编译错误 · `NOANS` 没做出来/不会 · `''` 未填。完整记录里加一个下拉（算法分区显示，其他分区隐藏）；速记可不填。
5. **最小反例**：`mistakes.counterexample TEXT NOT NULL DEFAULT ''`（≤1000 字，纯文本，等宽显示）。放在每条易错点上，占位提示“一个能让原代码出错的最小输入，例如：n=1 时输出 0，应为 1”。**复习卡片的背面要把它放在最显眼的位置**（它是最好的回忆线索），后面 B 项还会用它。
6. **接口**：`GET /api/error-taxonomy` → `{causes:[{code,label,hint}], verdicts:[{code,label}]}`；问题的创建/编辑接受 `verdict`；易错点接受 `counterexample`；校验与长度上限；导出 JSON、数据注销、扩展导入（`routers/plugin_api.py`，不传就空）、导入向导都要照顾新字段。
7. **统计跟着改**：`typical.py`、薄弱点页、总览里的错因相关统计、`today_sign.py` 里的 `TAG_JI` 都改成基于词表 code；薄弱点页新增两块小图：**判题类型分布**（WA/TLE/RE… 的横向条）和**最常见错因 Top 3**；AI 薄弱点分析的材料里带上 `verdict` 和 `counterexample`（有就带，注意长度截断，不要突破现有的提示词边界保护）。
8. **前端**：新增记录页、编辑题目、易错点编辑处，把标签输入换成**词表小标签（点选）**，并保留“其他”；样式要和现有表单一致且好看（词表小标签用印章/批注风格，不要普通灰色 chips）。

### 验收
迁移映射测试、接口校验测试、前端行为测试（选/取消/至少一个的提示）、导出/注销/扩展导入不报错、统计页能显示新分布；两套主题；旧数据升级后统计页不空。

## B. 复习 = 重做，不只是回忆

### 问题
算法题的“复习”本质是**重做**，不是回忆。现在的主循环是“看错因 → 自评 0/3/4/5”，自评容易虚高（觉得自己会了，其实写不出来）。

### 要做的（只增强算法分区，其他分区保持原样）
1. **三种复习方式**，在“显示错因”之后让用户选（算法分区默认引导到前两种）：
   - **默写关键代码**（该题有“正确代码”时可用）：显示题名、最小反例、你记的错因，给一个**空白代码编辑区**让用户把关键几行写出来；点“对照”后做**与空白/注释无关的逐行对比**（纯前端，规范化后按行 diff，高亮缺失和多余的行，给出相似度）。相似度建议映射：≥0.85 → 4，0.6–0.85 → 3，<0.6 → 0；用户仍可手动调整最终评分，但**要把“系统建议分”和“用户最终分”都记下来**（用来看自评是否虚高）。
   - **去原题限时重做**（该题有来源链接 `source_url` 时可用）：选时限（10/15/30 分钟，默认 15），点“开始”在新标签页打开原题，页面上有倒计时；回到本页后只问一个问题：**“做完了吗？”**，三个按钮：一次做对（建议 4，若用时不到时限一半可建议 5）/ 做对了但卡了很久（3）/ 没做出来或看了题解（0）。同样记录建议分和最终分。
   - **只回忆**（原来的自评）：保留，但卡片上标一个小标记“自评”，并在统计里区分。
2. **防自评虚高的轻提示**：同一条易错点最近 14 天内“只回忆”打了高分却又在下次评成低分（≥2 次）时，下次复习自动**默认选重做**并提示“这条用重做更靠谱”。
3. **数据（迁移 81）**：`reviews` 加 `mode TEXT NOT NULL DEFAULT 'recall'`（`recall`/`rewrite`/`redo`）和 `evidence TEXT NOT NULL DEFAULT ''`（小 JSON：`{"suggested":4,"final":3,"similarity":0.82,"seconds":412}`，服务端校验类型和长度 ≤ 500 字符）。评分接口 `POST` 复习结果时接受可选的 `mode` / `evidence`；**评分档位仍是原来的 0/3/4/5，间隔算法不变**。离线复习队列（`offline-sync.js`、`offline-review.js`）要带上这两个字段。
4. **设置**：账号里加“复习方式偏好”：重做优先（默认）/ 只回忆；专注模式也要走同样的流程。
5. **统计**：总览或复习结束页加一句“本周重做通过率 X% · 自评平均比重做高 Y 档”（有数据才显示）。

### 验收
三种方式的行为测试（对照 diff、倒计时、评分建议与最终分都入库）、离线队列带新字段、旧客户端不传新字段时服务端兼容（默认 `recall`）、两套主题、减少动画、手机宽度可用。

## C. 代码结构：`main.py` 与 `app.js` 拆分、理顺依赖

### 现状（我量过）
- `main.py` 2953 行、123 个函数；各路由里用 `main.<name>` 间接引用共 **928 处**——这是为了让测试里 `monkeypatch.setattr(main, ...)` 生效的权宜之计。
- `static/app.js` 5838 行、174 个函数，没有构建步骤；约 **52 个测试文件**直接读 `app.js` 源码做字符串断言；每次改静态资源要手动同步一堆 `?v=` 和测试里的版本 pin（我已经为此反复做了很多次）。

### 目标（不改任何用户可见行为）
- `main.py` 只保留应用装配（创建 `app`、中间件、挂载路由、启动初始化）≲ 800 行；业务逻辑和常量进入有明确职责的模块；
- 路由直接 `from xxx import yyy`，**不再出现 `main.<name>`**；测试的 monkeypatch 目标改到真正定义该名字的模块；
- `app.js` 拆成按领域划分的多个文件（每个 ≲ 600 行），仍是普通 `<script defer>`、**不引入构建步骤**，共享状态收进一个命名空间对象而不是几十个顶层变量；
- 测试里的版本 pin 不再写死数字（见 C3）。

### 分步（每步单独交付、全量测试全绿、可独立回滚）
**C1 后端：**
1. 先定模块划分并写在 REPORT（建议：`core/`（配置与常量、限流、数据库连接、鉴权、通用工具）、`models/`（pydantic 输入模型）、以及把 main.py 里已有的区块各自搬走：草稿演算区、微信提醒（Server酱/PushPlus）、榜单、Anki 导出、套路目录与归类、套餐/额度等）。
2. **每搬一个区块就改一批路由的引用并同步改测试的 monkeypatch 目标**，每步测试全绿再继续。`main:app` 入口（`uvicorn main:app`、Dockerfile、部署脚本）**必须保持不变**。
3. 过渡期允许 `main.py` 重新导出旧名字，但**最终状态**要清掉（grep `main\.\w` 在 `routers/` 下应为 0 或只剩 `main.app`）。
4. 不得改变任何接口的路径、字段、状态码、错误文案；不得改数据库结构。

**C2 前端：**
1. 在 `static/app/` 下按领域拆分（建议：核心（api/会话/路由/消息）、总览、复习与专注、记录表单、笔记粘合、论坛、小组、榜单、账号设置、管理后台等），`app.js` 退化成启动文件。
2. 因为没有构建，用 `<script defer>` 顺序保证依赖；共享状态放进 `window.OY`（一个命名空间对象），不要新增全局变量。
3. 提供一个测试辅助 `tests/static_helpers.py::app_source()`：返回拆分后所有 app 文件拼起来的文本，**把那 52 个读 `app.js` 的测试改成读它**，尽量不改断言本身。

**C3 版本 pin 去数字化：**
把测试里写死的 `app.js?v=NN`、`("app.js", NN)`、`versions["app.js"] == "NN"` 这类断言，改成用辅助函数从 `index.html` 读出当前版本，然后只断言**关系**（版本存在、脚本顺序正确、被改动的资源版本号变了——可以对照 `git diff` 或一份版本清单文件）。目的：以后改静态资源不再需要手工改几十个测试。

### 验收（C 整体）
- 全量测试全绿，**行为零变化**（我会在本地样本环境里点一遍主要页面核对）；
- `main.py` ≲ 800 行，`app.js` ≲ 2500 行，各新模块 ≲ 600 行；
- REPORT 里列出：模块划分图、每个区块搬到哪、测试里改了哪些 monkeypatch 目标、统计前后行数。
- **风险提示：** C 会和其他任务大面积冲突。请从我告诉你“可以开始 C”的那一刻的 main 开始做，做的时候不要夹带任何功能改动。
