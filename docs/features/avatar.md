
## 头像

登录用户可以在页面顶部上传/更换/移除自己的头像（`POST`/`DELETE
/api/me/avatar`），体验账号不支持（跟发帖、评论、举报是同一条口子）。
头像显示在讨论区作者、个人资料、小组成员和昨日之星里；连续打卡榜只列用户名与天数。
没上传过
头像的用户，前端用用户名首字母 + 按用户名哈希出的纯色圆形代替，不需要
服务端准备默认头像图片。

**审核策略是"先上线、事后举报"，不做上传前的人工审核**：上传成功立即
对所有登录用户可见。原因和讨论区发帖一致——这是邀请码内测的小圈子，
人工预审每一张图会显著拖慢体验，也不现实（没有专职审核人力）。

上传时的校验完全基于解码后的真实图片内容，不信任文件名后缀或请求头
声明的 `Content-Type`：

1. 大小限制 2MB（`AVATAR_MAX_BYTES`），超过直接拒绝，不做部分读取。
2. 用 Pillow 打开并 `verify()`；这一步之后的 Image 对象不能再用来处理，
   必须从同一份字节重新 `open()` 一次，再 `load()` 强制完整解码——两步
   都是为了防止"文件头合法但数据被截断/伪造"的图片绕过校验。
3. 只认 `image.format` 解码出来的真实格式（`JPEG`/`PNG`/`WEBP`），拒绝
   其他一切格式，即使是 Pillow 能正常解码的真实图片（比如 BMP）。
4. 不直接保存用户上传的原始字节：统一重新编码——按短边居中裁剪成正方形、
   缩放到 256×256、转成不透明 JPEG（半透明图片先合成到白色背景上，
   不是简单丢弃 alpha 通道），顺带清掉原图可能带的 EXIF 等元数据。

文件存在 `AVATAR_DIR`（默认 `data/avatars/{user_id}.jpg`，跟数据库文件
一样以项目目录为基准解析，备份复制整个 `data` 目录时会一起带上）。每次
上传或删除都会把 `users.avatar_version` 原子加一，前端用
`/api/users/{id}/avatar?v={avatar_version}` 这种带版本号的 URL 做缓存
失效，读头像的接口本身可以放心用较长的 `Cache-Control`。

### 举报头像

复用讨论区"先上线、事后举报"的思路，但举报记录单独放在 `avatar_reports`
表，不是塞进 `reports` 表加一列——`reports` 表已有的 CHECK 约束（帖子/
评论二选一）没法通过 `ALTER TABLE` 修改，SQLite 改已有 CHECK 约束必须
整表重建；新开一张结构类似的表可以让新库和旧库共用一份 schema，不用为
这一个改动单独写"重建表"迁移。限流复用和帖子/评论举报同一个按
`user_id` 计数的桶（`REPORT_LIMIT`），管理后台的举报队列是三种举报类型
合并后按时间排序的结果，每条都带 `type` 字段（`post`/`comment`/`avatar`）
供前端区分。

管理员在队列里处理头像举报时能：

- **清除该头像**（`DELETE /api/admin/users/{id}/avatar`）：删掉磁盘上的
  文件、`avatar_version` 加一，同时把这个用户名下所有待处理的头像举报
  一并标记为已处理。用户本人再次打开时会看到自己变回了默认头像。
- **忽略举报**（`POST /api/admin/avatar-reports/{id}/resolve`）。
- **封禁作者**（复用现有的 `POST /api/admin/users/{id}/ban`）。
